# Xibo CMS on Coolify

This is a **standalone** Compose application. Select [`docker-compose.yml`](docker-compose.yml), not the [upstream root Compose file](../docker-compose.yml); do not merge the two files. The root installation files are left unchanged.

## Provenance and compatibility

Baseline: [Xibo's official xibosignage/xibo-docker repository](https://github.com/xibosignage/xibo-docker), default branch `master`, commit [`2b8c3e1b1239c2551fc445270b9c59c8c3dc0929`](https://github.com/xibosignage/xibo-docker/commit/2b8c3e1b1239c2551fc445270b9c59c8c3dc0929) (fetched 2026-10-22). The application matches that commit's MySQL 8.4, XMR 1.4, CMS release-4.5.5, memcached and QuickChart services. Image tag defaults match the upstream Compose tags at this commit, not an assumed latest release; QuickChart's untagged upstream image implicitly uses `latest`. Mutable tags (including memcached's `alpine` and QuickChart's `latest`) can still change upstream. Review the official installation/upgrade guidance before changing versions.

The deliberate differences from [upstream Compose](../docker-compose.yml) are: one Coolify-selectable file, host-absolute persistent bind mounts instead of Compose-relative `./shared`, a Coolify-managed domain instead of publishing CMS port 80, explicit environment variables instead of an untracked `config.env`, and a configurable published XMR port. The CMS and MySQL share **one** required database password. No proxy labels, generated service URLs, or implicit second Compose file are needed. This is an integration recipe, not a claim of official Xibo/Coolify support.

## Deployment

1. In Coolify, create a **Git-based Docker Compose application** for this repository/branch. Set **Build strategy** to **Compose**, **Base Directory** to the repository root (`/` in Coolify's path UI) and **Docker Compose Location** to `/coolify/docker-compose.yml` (or the equivalent path relative to the configured base directory). Select only this file; do not select a root override or the upstream Compose file. Coolify UI names/leading slash conventions may vary by version: confirm the resolved location in its configuration before deployment.
2. In the application's **Environment Variables**, set `MYSQL_PASSWORD` to a new strong secret for a *new* install, `CMS_SERVER_NAME` to the public DNS hostname (no protocol or path), and `XIBO_DATA_DIR` to a stable **absolute directory on the Docker host**, for example `/srv/xibo-coolify`. Mark passwords as secret; keep them out of Git and CLI logs. For an existing database, use its **existing** CMS MySQL password, not a newly generated one. Configure `CMS_SMTP_SERVER`, `CMS_SMTP_USERNAME`, `CMS_SMTP_PASSWORD` and the other SMTP variables in the Compose file as needed for mail delivery; empty SMTP fields do not provide a working mail relay. Values in Coolify's UI must be available during Compose interpolation (build/deploy time), not only as runtime-only variables. Do not set `MYSQL_DATABASE`, `MYSQL_USER`, `MYSQL_HOST` or `XMR_HOST` separately: the file fixes them consistently for the included services.
3. On the **Docker host**, provision the chosen data directory on persistent storage before deployment. It must be writable by the database and CMS containers, and its `db` and CMS subdirectories must be owned/permissioned appropriately for their container processes. Bind mounts use upstream's `:Z` private SELinux relabel option; verify host SELinux and filesystem behavior (including backup agents) before using pre-existing paths. Never put data under an ephemeral checkout or a path that Coolify may remove. The `db`, `backup`, `cms/custom`, `cms/library`, `cms/web/userscripts`, and `cms/ca-certs` subdirectories persist; test writes and backups after deployment. Keep the DB and library on the same host across redeploys.
4. In **Domains**, add an `https://` domain for the **`cms-web` service**, routing to its internal **port 80**; configure DNS to point at the Coolify host and ensure the Coolify proxy can reach it. The CMS has no public host `80:80` binding. Terminate TLS at the Coolify proxy. Set `CMS_SERVER_NAME` to the same hostname and verify Xibo's public URL/proxy behavior after first start; installation-specific URL/HTTPS settings may need adjustment in the CMS. Do not add a `traefik.*` router rule with a placeholder host.
5. XMR is **not HTTP** and cannot use the CMS web domain route. XMR is published on host TCP port `9505` by default (`XIBO_XMR_PORT` changes the host port; `XIBO_XMR_BIND_IP` defaults to `0.0.0.0`). If remote players require XMR, allow that TCP port through the host/cloud firewall to the required clients, use a reachable public address, and configure the XMR public address/port in Xibo's CMS settings as appropriate for your players. Restrict access where possible; if XMR is not needed externally, set `XIBO_XMR_BIND_IP=127.0.0.1` or restrict the firewall. Check for port conflicts before deployment. Do **not** route XMR as HTTPS traffic through the HTTP proxy.

Coolify's [Git Compose configuration](https://coolify.io/docs/applications/builds/docker-compose) describes selecting the file and assigning domains per service; [Compose persistent storage](https://coolify.io/docs/applications/configuration/persistent-storage) documents why mounts belong in the Compose file. Check your installed Coolify version for UI and path differences. Relative bind mounts have deployment-specific semantics, hence the required host-absolute path here. No Compose file-merging feature is assumed.

### Image tag overrides

The standalone [Compose file](docker-compose.yml) uses these optional tag variables (image repositories remain fixed):

| Coolify environment variable | Default tag | Image |
| --- | --- | --- |
| [`MYSQL_IMAGE_TAG`](docker-compose.yml:5) | `8.4` | `mysql` |
| [`XMR_IMAGE_TAG`](docker-compose.yml:17) | `1.4` | `ghcr.io/xibosignage/xibo-xmr` |
| [`CMS_IMAGE_TAG`](docker-compose.yml:24) | `release-4.5.5` | `ghcr.io/xibosignage/xibo-cms` |
| [`MEMCACHED_IMAGE_TAG`](docker-compose.yml:55) | `alpine` | `memcached` |
| [`QUICKCHART_IMAGE_TAG`](docker-compose.yml:61) | `latest` (the implicit tag of the previously untagged image) | `ianw/quickchart` |

To override a tag, add the corresponding variable in the Coolify application's **Environment Variables** and set it to the tag only (for example, set [`CMS_IMAGE_TAG`](docker-compose.yml:24) to a reviewed CMS release tag, not a full image name). Make it available during Compose interpolation at build/deploy time, then redeploy. Leave a variable unset to use its default; an empty value also falls back to the default. These variables select image tags only, not repositories or application configuration.

## Existing installations, backup and recovery

**Do not deploy over an existing installation until its data is identified and backed up.** The old fork used *named* Docker volumes (`db`, `custom`, `backup`, `library`, `userscripts`, `certs`) with project-prefixed actual names. This file uses *host bind mounts* and **will not automatically discover or reuse** those volumes. The old fork also declared `customtheme` without mounting it; inspect it before deciding whether any data in it needs migration. A separate upstream bind-mount installation may already have the `shared/` layout: set `XIBO_DATA_DIR` to the absolute path to that existing `shared` directory *only after* checking permissions, labels, DB credentials, software compatibility and backups. Avoid running both stacks on the same data.

For a named-volume installation, first record the old deployment's Compose project name, actual volume names and mountpoints using `docker volume ls` and `docker volume inspect` **on its host** (never infer volume identities from this repo). Stop the old application cleanly; take a verified consistent MySQL dump or cold backup, and back up the CMS library, custom content, certificates, user scripts and backup directory. With both applications stopped, copy each old volume into its corresponding host directory (`db` → `db`, `custom` → `cms/custom`, `backup` → `backup`, `library` → `cms/library`, `userscripts` → `cms/web/userscripts`, `certs` → `cms/ca-certs`) preserving file ownership, permissions and data integrity. Relabel/adjust ownership if SELinux applies. Do not copy a live MySQL data directory or start two database instances against the same data; a logical SQL restore to a fresh compatible database is safer across incompatible versions. Verify the old MySQL version, CMS version and Xibo's documented upgrade path *before* attempting to reuse database files; the current upstream tags alone do not establish upgrade compatibility. Keep the original volumes and an off-host backup until login, content, player connectivity and restore have all been tested. Do not remove old volumes as part of this migration.

Back up **both** the database (and/or consistent dump) and the persistent CMS library/custom assets regularly, along with certificates, scripts and application settings. The upstream CMS writes automated DB backups to `backup`; verify that job and retention rather than treating those backups as your only recovery plan. Keep the `MYSQL_PASSWORD` secret safe for restores. A new deployment with an empty `XIBO_DATA_DIR` creates a **new, empty installation**.

## Updating and validating

The Git branch for this work starts at the official baseline above. Changing the image tag variables is **not** a substitute for reviewing upstream structural changes. Before future updates, fetch `upstream/master`, compare the upstream [root Compose file](../docker-compose.yml) and [environment template](../config.env.template) for changes in services, image tags, variable names and mounts, then consciously adapt the standalone [Compose file](docker-compose.yml). Check Xibo's documented DB migrations and release compatibility; test a backed-up staging copy first. No automatic tag tracking or image compatibility guarantee is implied.

For a local syntax check with **dummy nonproduction** values, run (without pasting the rendered output into logs):

```sh
MYSQL_PASSWORD=not-a-real-secret CMS_SERVER_NAME=cms.example.invalid XIBO_DATA_DIR=/srv/xibo-test docker compose -f coolify/docker-compose.yml config --quiet
```

Also verify host paths and permissions, domain routing, TCP XMR reachability, SMTP delivery and backup/restore on the actual deployment host. `docker compose config` validates interpolation and syntax but cannot prove Coolify routing, image behavior, database migrations or firewall reachability. Optional features from [upstream's template](../config.env.template), such as `CMS_ALIAS`, PHP upload limits, cron options, custom themes and non-default cache/chart settings, are **not** wired by this minimal file; add their explicit environment mappings or mounts only when required, and verify them against the installed CMS version. In particular, upstream documents a custom-theme path but does not mount it in its current default Compose file.
